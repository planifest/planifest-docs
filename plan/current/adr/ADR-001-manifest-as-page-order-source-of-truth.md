# ADR-001 - Manifest as single source of truth for doc page order

**Component:** web-app

## Context

`build-docs.js` currently discovers doc pages by calling `fs.readdirSync()` on the `planifest-docs/` directory. This produces an unpredictable ordering (filesystem-dependent, OS-dependent) and contains no title metadata beyond what can be inferred from the markdown `# heading`. The top nav is hardcoded in the template with a single "Overview" link. There is no mechanism for prev/next navigation.

To add manifest-driven top nav and prev/next links, the build script needs an authoritative, ordered list of pages with human-readable titles. The question was: where does that authoritative list live, and in what format?

---

## Decision

A JSON file at `src/web-app/docs.manifest.json` is the single source of truth for page order and titles. It contains an ordered array of `{ "file": "NN-slug.html", "title": "Human Title" }` entries. `build-docs.js` reads this manifest to determine page sequence, generate nav links, and compute prev/next relationships. Pages not listed in the manifest are not included in nav; `build-docs.js` emits a warning for any `.md` source file that has no manifest entry.

JSON was chosen over YAML or a JS module because it requires no parser dependency (Node.js `JSON.parse` is built-in), is universally editable by humans and agents, and is already the format used by `public/sitemap-data.json` in this codebase.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Filesystem order (current) | Zero config | OS/filesystem-dependent ordering; no explicit titles | Non-deterministic; no way to express intent |
| Frontmatter in markdown files | Co-located with content; standard pattern | Requires parsing every .md file to extract order; complicates build-docs.js significantly | Adds complexity for a static list that rarely changes |
| JS/TS config module | Type-safe; IDE completion | Requires transpilation or dynamic import; adds toolchain complexity | Overkill for a flat ordered list |
| YAML manifest | Human-readable | Requires a YAML parser dependency | No advantage over JSON for this data shape; adds a dependency |

## Affected Components

| Component | Impact |
|-----------|--------|
| web-app | `build-docs.js` reads manifest at build time; manifest must be kept in sync when doc pages are added or removed |

---

## Consequences

**Positive:**
- Page order is explicit, deterministic, and version-controlled
- Adding a page requires one manifest edit — a single source of truth, no scattered nav updates
- Manifest is human-readable and editable without tooling
- Consistent with the existing `sitemap-data.json` pattern already in the codebase

**Negative:**
- Adding a new doc page requires two steps: add the `.md` source AND update the manifest — easy to forget one
- Manifest can drift from the filesystem if pages are added/removed without updating it

**Risks:**
- A developer adds a `.md` file but forgets to update the manifest → new page is silently excluded from nav. Mitigated by: build-docs.js warning on undeclared pages (R-002 in risk register).
