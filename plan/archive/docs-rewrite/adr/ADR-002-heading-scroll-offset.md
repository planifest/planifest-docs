# ADR-002 - CSS scroll-margin-top for fixed nav offset

**Skill:** adr-agent
**Tool:** Claude Code
**Model:** claude-sonnet-4-6
**Feature:** docs-rewrite
**Component:** src/web-app
**Status:** accepted
**Date:** 2026-05-16

---

## Context

Doc pages render a `position: fixed` navigation bar (~48px tall). When a user clicks a hash link in the table of contents (e.g. `#getting-started`), the browser scrolls the target heading to the top of the viewport — but the fixed nav overlaps it, hiding the heading. This was reported as hash links appearing to do nothing or scrolling to the wrong position.

Additionally, Mermaid diagram rendering (async, post-DOMContentLoaded) shifts page layout after the browser's initial hash scroll, resetting the scroll position to the top.

---

## Decision

1. Apply `scroll-margin-top: 72px` to all headings (`h1`–`h6`) in `style.css`. This is a native CSS property that instructs the browser to leave 72px of clearance above the element when scrolling it into view — including for hash navigation.

2. Set `mermaid.startOnLoad: false` and call `mermaid.run()` explicitly in `main.ts`. After the returned promise resolves, re-scroll to the current hash if one is set.

The 72px value provides a 24px buffer above the 48px nav, matching the visual padding used in the design.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| JavaScript scroll handler on `hashchange` and load events | Full control over scroll position | Requires JS, fights browser default behaviour, fragile across browsers | Rejected — CSS `scroll-margin-top` is the semantic, browser-native solution |
| Padding-top on each section element | Works without JS | Alters visual layout; affects spacing even when not hash-navigating | Rejected — side effects on visual layout |
| `scroll-padding-top` on `html` element | Single rule, applies globally | Affects all scroll-into-view behaviour, not just hash links; less precise | Considered as complement but `scroll-margin-top` on headings is more targeted |

---

## Consequences

**Positive:**
- Hash navigation works correctly with a fixed nav — the heading is visible below the nav after scroll
- Mermaid diagrams render without resetting the scroll position
- Pure CSS solution for scroll offset — no JS required for the core behaviour

**Negative:**
- `72px` is hardcoded; if nav height changes, this value must be updated manually

**Risks:**
- See R-002 in risk register — assessed as low likelihood, accepted.
