# ADR-002 - Nav injection via template placeholder rather than post-processing

**Tool:** Claude Code

**Feature:** 0000001-doc-nav
**Component:** web-app
**Status:** accepted

## Context

`build-docs.js` uses a simple string-replacement template (`{{TITLE}}`, `{{CONTENT}}`) to produce each doc page. To inject manifest-driven nav links and prev/next pagination, the build script needs a mechanism to insert dynamically generated HTML into the page at specific locations.

Two structural approaches exist: (1) extend the placeholder pattern already in use, adding `{{DOC_NAV_LINKS}}` and `{{PREV_NEXT_NAV}}` tokens; or (2) post-process the generated HTML using regex or a DOM parser to locate insertion points and mutate the output.

---

## Decision

Extend the existing placeholder pattern. Add `{{DOC_NAV_LINKS}}` to the template's `<div class="nav-links">` section and `{{PREV_NEXT_NAV}}` inside `<main>` after `{{CONTENT}}`. `build-docs.js` generates the nav HTML from the manifest and substitutes these tokens before writing each file. The existing `{{TITLE}}` and `{{CONTENT}}` replacements already demonstrate this pattern works.

For the prev/next block specifically — since it is per-page (varies by position in manifest), it is injected via string replacement into the per-page HTML output rather than the shared template token, to avoid the token needing per-page context at template-load time.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Regex post-processing of generated HTML | No template changes needed | Brittle — breaks if nav markup changes; hard to reason about correctness | Fragile and hard to maintain |
| DOM parser (e.g. `node-html-parser`) | Semantic, robust to markup changes | Adds a runtime dependency; overkill for a known, controlled template | Adds dependency; template is already controlled |
| Separate template per page | Full control per page | Massive duplication; defeats the purpose of a shared template | Violates DRY; maintenance burden |
| Placeholder pattern (chosen) | Consistent with existing `{{TITLE}}`/`{{CONTENT}}` pattern; zero new dependencies; explicit and readable | Placeholder must exist in template — fails loudly if missing (which is the correct behaviour) | N/A — this is the chosen option |

## Consequences

**Positive:**
- Zero new dependencies — pure string replacement using existing Node.js built-ins
- Consistent with the mental model already established by `{{TITLE}}` and `{{CONTENT}}`
- Fails loudly and predictably if placeholder is missing (easy to detect, easy to fix)
- Template remains readable — the placeholder clearly marks where nav will appear

**Negative:**
- Template must be kept in sync with the placeholder convention — a human editing `doc-template.html` directly could inadvertently remove the placeholder
- Prev/next injection is slightly different from top nav (per-page string replace vs. template token) — two slightly different mechanisms in the same script

**Risks:**
- External `doc-template.html` edited by hand could drop `{{DOC_NAV_LINKS}}` → nav disappears silently. Mitigated by: build-docs.js validates placeholder presence and exits with a clear error if missing (R-004 in risk register).
